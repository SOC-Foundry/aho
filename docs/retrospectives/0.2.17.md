## What worked

Five things held under load across the iteration:

1. **Chat-first hard meta-rule.** Plan docs and executor prompts originated in chat; container session implementations followed verbatim. Discipline did not slip across W0–W4. Per-iteration drafter ↔ executor split stayed clean — drafter authoring artifacts in chat, executor implementing in container, no implementation work bleeding into drafter sessions and no plan-doc revisions bleeding into executor sessions.

2. **Adversarial Authorship state machine produced honest dispositions.** Auditor surfaced findings that were either (a) genuine drafter-arbitration work (W2/W3/W4 self-audit findings on registered-anchor IDs that were drafter-resolvable) or (b) structural pre-checks correctly flagging Pillar-11-evidence prose for human review. No auditor self-audit produced `clean` for an artifact with substantive defects across W2/W3/W4. The state machine `pending_audit → audit_complete → drafter_arbitration → operator_sign` advanced through every workstream without a forced edit.

3. **F-0.2.17-W1-003 Pillar 11 incident surfaced voluntarily by executor.** The W1 D3 broker round-trip equivalence gate's design surfaced a Telegram bot token to executor stdout. Executor (Claude Code) recorded the incident as F-0.2.17-W1-003 in the acceptance archive at write time, called out the contradiction with CLAUDE.md `No reading secrets` rule explicitly, and recommended operator-side rotation. Auditor (Gemini at W1, llama at W2+) accepted as `pass_with_findings` rather than `fail` on the basis of the executor's transparent self-reporting. The system functioned as Adversarial Authorship is designed to function: an incident that would have been silent under a single-agent model surfaced because the protocol's drafter ↔ executor boundary made stdout-to-agent a recordable event.

4. **W3 → W4 progression from partial to structural closure.** F-0.2.17-W2-006 (auditor reference-resolution gap) was first addressed in W3 by adding RAG enrichment to the audit prompt. The fix closed 1 of 2 demonstrated false positives; the residual case (W2 self-audit F-0.2.17-W1-003) persisted under the same prompt rule, same context shape, same model. W4 D1 landed the deterministic post-hoc filter — a structural fix that does not bet on small-model prompt-following. Both demonstrated false positives now structurally closed at W4. The iteration-over-iteration sharpening loop (capability gap → partial fix → structural closure) ran through to completion within the iteration.

5. **Cross-project contamination vigilance held.** Zero contamination instances surfaced across W0–W4 against verified canonicals (Eleven Pillars, ADR numbering, gotcha registry, version labels). The discipline established at 0.2.15 close ("verify against aho canonical references; do not fabricate version numbers or ADR numbers") continued to function in 0.2.17.

## What didn't work

Three things failed or near-failed across the iteration:

1. **Drafter-side design specification of secrets-test value-printing was wrong on Pillar 11 grounds.** The W1 plan-doc line 63 specified `aho secrets-test` as a value-equality acceptance gate that printed the decrypted value to stdout. The specification was the root-cause defect for F-0.2.17-W1-003 — drafter-side design responsibility, not executor implementation flaw. Any acceptance gate that surfaces a decrypted secret to any agent stdout is a Pillar 11 violation by construction; the plan-doc design did not internalize this. ADR-0009 captures the gotcha (hash-fingerprint contract or broker-side equality boolean as the only acceptable shapes). The W2/W6 secrets-test redesign + F-0.2.17-W1-001 subcommand removal close the production-image leakage path; F-0.2.17-W1-003 itself closes only when operator rotates the burned token (post-0.2.17, hard gate before 0.3.x).

2. **Drafter conflated "executor" role with "Claude Code recipient" three times in chat.** Across multiple plan-doc authoring turns, the drafter slipped between "executor implements per the plan-doc" (architectural framing — executor is a seat, not a tool) and "Claude Code does X" (delivery-mechanism framing — Claude Code is the thing receiving the prompt). The conflation tends to produce plan-doc text that reads as if the drafter is talking to Claude Code directly rather than to the executor seat. Operator surfaced this repeatedly; drafter corrected each time but the slip recurred. Worth carrying as a drafter-process hazard for 0.3.x — the seat language is load-bearing for the protocol's clean semantics, and conflation erodes it.

3. **Initial W4 plan doc didn't anticipate auditor-RAG integration.** When W3 closed, F-0.2.17-W3-001 surfaced as a follow-on need: small-model prompt-following inconsistency was the residual problem after RAG enrichment closed the W0 case. The W4 plan-doc was refreshed post-W3-close with the deterministic post-hoc filter as a new D1 — drafter recognized the gap and re-planned. The original plan-doc shape was insufficient. Not a process failure (the refresh was the right move), but recording honestly: the plan-doc as initially drafted would not have closed the residual problem, and the iteration's success depended on drafter-side recognition that the plan needed re-shape mid-iteration.

## What surfaced unexpectedly

Five surprises across the iteration; all four 0.2.17-era are recorded as carry-forwards. Two of the four are pre-0.3.x hard gates:

1. **Pasta networking SNATs container → host traffic to host primary IP arriving on lo (F-0.2.17-W1-002).** W1 D5 firewall rules accepting source `127.0.0.0/8` + `169.254.0.0/16` did not cover the pasta-NAT path. Container → `host.containers.internal` connections arrive on `lo` with the host's primary IP as source — neither range applies. Operator amended via `nft insert rule inet aho_ollama input iif lo tcp dport 11434 accept`. Discovery cost: D5 Gate 2 timeout, ~30 minutes of investigation. Documented in deployment notes; ADR-0009 references the `iif`-scoped rule pattern as the canonical shape for any future container-host firewall design.

2. **GitHub Packages last-tag DELETE rejection (F-0.2.17-W0-003).** GitHub's package API rejects per-version DELETE on the last tagged version of a package; the package itself must be deleted instead. Discovered during the W0 B2.5 push-pull round-trip cleanup. Pre-flight automation should encode the package-level DELETE fallback explicitly. Documented as a deployment-doc lesson; carries forward.

3. **NVIDIA CUDA tag scheme drift (F-0.2.17-W0-005).** ADR-0007's GPU-passthrough validation snippet referenced `docker.io/nvidia/cuda:12.0-base`. By W0 amendment time, that tag was retired in NVIDIA's tag scheme; current scheme is `12.x.y-base-ubuntu24.04`. Validation used `12.6.3-base-ubuntu24.04`. Pre-flight automation should query the registry's current tag set or pin with a "verified at <iteration>" marker. Documented as a deployment-doc lesson.

4. **ChromaDB iteration-context index staleness (F-0.2.17-W4-001).** W4 D7 self-audit RAG enrichment showed three carry-forwards (F-0.2.17-W3-001, F-0.2.17-W3-002, F-0.2.17-W2-006) as `unverified` despite all three being added to `carry-forwards-0.2.16.md` at W2/W3 closes. The IDs are registered; the ChromaDB index built during W2 D1 pre-seed has not been refreshed. `gap_carry_forward_writer.append_to_file` writes to the markdown file but does not trigger ChromaDB re-index. **The defect captured by W4-001 is exhibited by W4-001 itself**: an audit run today against any artifact citing F-0.2.17-W4-001 would correctly flag it as `unverified` for the same reason. Hook re-index into the writer's append path or schedule pre-audit re-index — W6 scope.

5. **Tailscale MagicDNS hijacked CachyOS mirrors (F-host-001).** Pre-W0 host issue surfaced during W0 Bucket 2 pacman work. Tailscale's "Override Local DNS" forced all DNS queries through MagicDNS, including queries explicitly directed at upstream resolvers. CachyOS mirror domains resolved to TEST-NET-3 addresses serving identical interception HTML. ~45 minutes of session time spent on the wrong RCA (mirror corruption hypothesis) before operator identified the DNS-layer cause. Resolution: Tailscale split-DNS rule excluding `cachyos.org`. Recorded as deployment-doc requirement: any aho host joining Tailscale needs explicit split-DNS rules carving out distro mirror domains. Documented via investigation lesson — DNS-resolution sanity check belongs in package-management RCA before the mirror hypothesis is pursued.

## Materiality status

The 0.2.17 evidence build for the [ADR-0010 materiality measurement protocol](../../artifacts/adrs/0010-materiality-measurement.md) spans **four iterations** (W0 / W1 / W2 / W3 acceptance archives), with the auditor primitive deploying first at W2 and stabilizing at W4. The four-bucket counter telemetry (`aho.materiality.claim_vs_artifact_mismatches.{caught_by_llama,caught_by_drafter,escaped}` + `aho.materiality.carry_forward_resolution_rate`) was wired at W2 D12 and emitted across W3 and W4. Three iterations of auditor-seat data accumulated:

- **W2 baseline** — auditor without enhancement. Self-audit produced false positive (F-0.2.17-W1-003 flagged "looks placeholder" despite being sealed-real). Counter `caught_by_llama` incremented for the finding — counted in the bucket but the increment recorded a fabricated defect, not an artifact-resident one.
- **W3 partial fix** — RAG enrichment via `audit_ref_lookup`. Closed 1 of 2 demonstrated false positives (W0 case closed; W2 self-audit case persisted under the same prompt rule).
- **W4 structural closure** — deterministic post-hoc filter. Both demonstrated false positives now structurally suppressed; F-0.2.17-W2-006 + F-0.2.17-W3-001 closed at W4 close. The W4 D1 filter does not depend on small-model prompt-following.

**N=4 is below the N≥8 falsifiability threshold.** Per ADR-0010, the protocol's qualified-validation status holds at 0.2.17 close. Full validation requires the threshold metrics (≥30% reduction in `escaped` vs baseline, non-zero `caught_by_llama` and `caught_by_drafter`, ≥60% carry-forward resolution rate within 2 iterations of flagging) to be exercised against an N≥8 evidence window. The data is being recorded honestly; the threshold is not yet exercised.

The qualified-validation status is **the honest characterization** at 0.2.17 close. Premature claims of full validation at N=4 would be exactly the rubber-stamping the architecture is designed to surface. The protocol's recording surface is functioning; its falsification surface is not yet exercised.
